# Памятка новичку для защиты лабораторной

## 1. Что это за проект

Это серверное приложение на Node.js и Express. Оно предоставляет REST API для работы с плейлистами совместного прослушивания музыки.

Проще говоря: клиент отправляет HTTP-запрос, сервер принимает его, проверяет данные, выполняет операцию над плейлистом и возвращает JSON-ответ.

## 2. Как быстро запустить проект

В папке проекта выполнить:

```powershell
npm.cmd install
npm.cmd start
```

Если нужна автоматическая перезагрузка при изменении кода:

```powershell
npm.cmd run dev
```

Проверка в браузере:

```text
http://localhost:3000/
http://localhost:3000/playlists
```

Браузером удобно проверять только `GET`. Для `POST`, `PUT` и `DELETE` используется Postman.

## 3. Как объяснить структуру

Можно сказать так:

> В `server.js` создается Express-приложение и подключается JSON-parser. В `routes` описаны маршруты. Контроллер принимает запрос и отвечает клиенту. Модель хранит и изменяет данные плейлистов. Такое разделение делает код понятным и позволяет позже заменить массив на базу данных.

## 4. Главные маршруты

| Метод | Маршрут | Что делает |
|---|---|---|
| GET | `/playlists` | возвращает все плейлисты |
| GET | `/playlists/:id` | возвращает плейлист по ID |
| POST | `/playlists` | создает новый плейлист |
| PUT | `/playlists/:id` | полностью обновляет плейлист |
| DELETE | `/playlists/:id` | удаляет плейлист |

## 5. Как показать работу API

### Получение списка

```text
GET http://localhost:3000/playlists
```

Ответ имеет статус `200` и содержит `count` и массив `data`. Изначально в массиве есть три плейлиста.

### Создание

```text
POST http://localhost:3000/playlists
Content-Type: application/json
```

Тело запроса:

```json
{
  "title": "Late Night Jazz",
  "description": "Джаз для совместного прослушивания",
  "owner": "dave",
  "isPublic": true,
  "tracks": [
    {
      "title": "Blue Hour",
      "artist": "Jazz Collective",
      "durationSec": 276
    }
  ],
  "listenersOnline": 1
}
```

Ожидаемый результат: статус `201 Created`, сервер присваивает новый ID.

### Получение одного объекта

```text
GET http://localhost:3000/playlists/4
```

Если объект создан, сервер возвращает его со статусом `200`. Если ID не существует, ответ будет `404`.

### Обновление

`PUT` отправляет полный набор обязательных данных на адрес конкретного ID. При успешном обновлении сервер возвращает статус `200` и измененный объект.

### Удаление

```text
DELETE http://localhost:3000/playlists/4
```

Успешное удаление возвращает `204 No Content` без тела. Повторный запрос `GET /playlists/4` должен вернуть `404`.

## 6. Валидация

Сервер не принимает некорректные данные:

- `title` и `owner` должны быть непустыми строками;
- `description` должна быть строкой;
- `isPublic` должен быть boolean;
- `tracks` должен быть массивом объектов;
- у каждого трека обязательны `title` и `artist`;
- `durationSec` и `listenersOnline` должны быть неотрицательными целыми числами;
- ID должен быть положительным целым числом.

При ошибке запроса возвращается `400` и поле `error` с объяснением причины.

## 7. Готовая речь на защиту

> Моя лабораторная работа — REST API для платформы совместного прослушивания музыки и создания плейлистов. Приложение написано на Node.js с использованием Express. Основной ресурс API — `playlists`.
>
> В проекте используется разделение на три уровня: маршруты, контроллеры и модель. Маршруты определяют HTTP-метод и URL, контроллеры проверяют запрос и формируют ответ, а модель выполняет операции с данными.
>
> Реализованы операции CRUD: получение списка и одного плейлиста, создание, полное обновление и удаление. Для успешных операций используются статусы `200`, `201` и `204`, а для ошибок — `400` и `404`.
>
> Входные данные проверяются до изменения модели. Сейчас данные хранятся в массиве в памяти, поэтому после перезапуска сервера возвращаются стартовые записи. Для production-версии я бы заменил массив на PostgreSQL или другую внешнюю базу данных.

## 8. Частые вопросы преподавателя

**Почему это REST API?**

Потому что приложение работает с ресурсом `playlists` через стандартные HTTP-методы и возвращает данные в JSON.

**Зачем нужен контроллер?**

Он отделяет обработку HTTP-запроса от хранения данных: проверяет входные значения, вызывает модель и выбирает статус ответа.

**Почему используется `201`, а не `200` при создании?**

`201 Created` означает, что новый ресурс был успешно создан.

**Что произойдет после перезапуска?**

Изменения исчезнут, потому что данные хранятся в оперативной памяти, а не в постоянной базе.

**Зачем нужен `process.env.PORT`?**

Cloud-платформа сама назначает порт через переменную окружения. Благодаря `process.env.PORT || 3000` приложение работает и в cloud, и локально.

**Как проверить ошибку?**

Отправить `GET /playlists/999` и получить `404`, либо выполнить `POST` без `title` и `owner` и получить `400`.

**Можно ли назвать это realtime-приложением?**

Пока это REST-основа предметной области. Настоящее обновление данных в реальном времени потребовало бы WebSocket или Socket.IO и постоянного хранилища.

## 9. Что важно не перепутать

- ресурс называется `/playlists`, а не `/contests`;
- начальный `GET /playlists` возвращает три записи;
- `DELETE` возвращает `204 No Content` без тела;
- данные не сохраняются после перезапуска;
- браузер сам по себе не отправляет `POST`, `PUT` и `DELETE` из адресной строки.
