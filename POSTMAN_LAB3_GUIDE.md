# Проверка лабораторной №3 в Postman

## Важно: примеры ниже соответствуют именно этому проекту

Текущий проект — API музыкальных плейлистов. В нём есть маршруты `/auth/register`, `/auth/login`, `/profile` и `/playlists`. Маршрутов `/currencies` в проекте нет, поэтому примеры с валютами из другого отчёта здесь не сработают. Защищённые действия администратора в этой версии относятся к созданию, изменению и удалению плейлистов.

Фактические ответы также немного отличаются от формулировок примера: регистрация возвращает объект `user` с полями `id`, `email`, `role`, профиль — объект `user` с этими же полями. Даты создания в ответе профиля нет, алиаса `/auth/profile` тоже нет. Используй `GET /profile`.

## 1. Запусти сервер

Убедись, что в корневом `.env` настроены PostgreSQL-переменные (`DATABASE_URL` и при необходимости `DATABASE_SSL`) и задан секрет JWT:

```dotenv
JWT_SECRET=сгенерированный_секрет_не_короче_32_байт
```

Если таблица пользователей ещё не создана, один раз выполни миграции:

```powershell
npm.cmd run db:migrate
```

Запусти сервер:

```powershell
npm.cmd run dev
```

В Postman используй базовый адрес `http://localhost:3000`. Оставь окно сервера открытым, пока проверяешь запросы.

## 2. Создай запрос регистрации

1. Создай в Postman новый HTTP Request.
2. Выбери метод `POST`.
3. Укажи URL `http://localhost:3000/auth/register`.
4. Открой **Body → raw → JSON** и вставь:

```json
{
  "email": "postman-user@example.com",
  "password": "StrongPass123"
}
```

5. Отправь запрос кнопкой **Send**.

Ожидается статус `201 Created` и ответ примерно такого вида:

```json
{
  "message": "Регистрация успешно завершена",
  "user": {
    "id": 1,
    "email": "postman-user@example.com",
    "role": "user"
  }
}
```

Значение `id` в твоём ответе может быть другим. Пароля и `passwordHash` в ответе быть не должно. Если отправить регистрацию повторно с тем же email, ожидается `409 Conflict`.

## 3. Выполни вход и получи JWT

1. Создай запрос `POST http://localhost:3000/auth/login`.
2. В **Body → raw → JSON** отправь те же email и пароль:

```json
{
  "email": "postman-user@example.com",
  "password": "StrongPass123"
}
```

3. Нажми **Send**. Ожидается статус `200 OK` и ответ:

```json
{
  "message": "Вход выполнен успешно",
  "token": "<тут будет JWT>",
  "expiresIn": "1h"
}
```

Скопируй значение `token` без кавычек. Это токен для следующих шагов; пароль в запросах к защищённым маршрутам больше не отправляется.

## 4. Проверь профиль с токеном

1. Создай запрос `GET http://localhost:3000/profile`.
2. Открой вкладку **Authorization**.
3. В **Type** выбери **Bearer Token**.
4. Вставь скопированный JWT в поле **Token**.
5. Нажми **Send**.

Ожидается статус `200 OK`:

```json
{
  "user": {
    "id": 1,
    "email": "postman-user@example.com",
    "role": "user"
  }
}
```

Профиль не содержит пароль или `passwordHash`. Дата создания пользователя в текущем ответе тоже не возвращается.

## 5. Проверь профиль без токена

Создай новый запрос `GET http://localhost:3000/profile`, на вкладке **Authorization** выбери **No Auth** и нажми **Send**. Ожидаются `401 Unauthorized` и ответ:

```json
{
  "error": "Требуется Bearer-токен"
}
```

Это демонстрирует, что профиль защищён middleware проверки JWT.

## 6. Проверь, что обычному пользователю запрещена запись

Войди как пользователь с ролью `user` и используй его токен. Создай запрос:

- Метод: `POST`
- URL: `http://localhost:3000/playlists`
- **Authorization → Bearer Token**: JWT обычного пользователя
- **Body → raw → JSON**:

```json
{
  "title": "Postman Test Playlist",
  "description": "Проверка ролевого доступа",
  "owner": "postman-user",
  "isPublic": true,
  "tracks": [
    {
      "title": "Demo Track",
      "artist": "Demo Artist",
      "durationSec": 180
    }
  ],
  "listenersOnline": 0
}
```

Ожидается `403 Forbidden`:

```json
{
  "error": "Доступ разрешён только администраторам"
}
```

Маршрут существует и токен принят, но роли `user` не хватает для операции — это проверка RBAC.

## 7. Назначь роль администратора и повтори запрос

Новая регистрация всегда получает роль `user`; публичного запроса для назначения себе администратора нет. В PostgreSQL выполни от имени владельца/администратора базы:

```sql
UPDATE users
SET role = 'admin'
WHERE email = 'postman-user@example.com';
```

Middleware загружает актуальную роль из базы при каждом защищённом запросе. Поэтому можно повторить запрос создания плейлиста с уже полученным токеном: повторный вход для обновления роли не требуется. Ожидается `201 Created`, а созданный плейлист будет в `data.id`. Запиши этот числовой ID — он понадобится для следующих запросов.

Если получен `500`, сначала проверь подключение к PostgreSQL и применение миграции. Если остался ответ `403`, проверь, что SQL обновил пользователя с тем же email и что запрос отправлен с его токеном.

## 8. Измени и удали тестовый плейлист

Для изменения отправь `PUT http://localhost:3000/playlists/<ID>` с Bearer-токеном администратора и JSON-телом плейлиста. Подставь ID, полученный после создания; у `title` и `owner` должны быть непустые строковые значения:

```json
{
  "title": "Updated Postman Playlist",
  "description": "Плейлист обновлён администратором",
  "owner": "postman-user",
  "isPublic": true,
  "tracks": [
    {
      "title": "Demo Track",
      "artist": "Demo Artist",
      "durationSec": 180
    }
  ],
  "listenersOnline": 0
}
```

Ожидается `200 OK`. Для удаления отправь `DELETE http://localhost:3000/playlists/<ID>` с тем же Bearer-токеном администратора. Ожидается `204 No Content` без JSON-тела.

Чтение остаётся открытым: `GET http://localhost:3000/playlists` возвращает список, а `GET http://localhost:3000/playlists/<ID>` — отдельный плейлист.

## Готовый текст для отчёта: проверка RBAC и вывод

Ниже приведены готовые фрагменты для отчёта по этому проекту. Предметная область — музыкальная платформа, поэтому в описании используются маршруты плейлистов, а не валют.

**Проверка отказа обычному пользователю (рисунок 7).** Для проверки RBAC был выполнен вход под учётной записью с ролью `user`, получен JWT и отправлен запрос `POST /playlists` с заголовком `Authorization: Bearer <JWT>` и корректным JSON плейлиста. Ожидаемый результат — статус `403 Forbidden` и сообщение «Доступ разрешён только администраторам». Маршрут создания плейлиста требует сначала пройти `authenticate` в `middleware/auth.js`, а затем проверку роли `isAdmin` из `middleware/isAdmin.js`; пользователь с ролью `user` не может создавать плейлисты. Чтение списка и отдельных плейлистов остаётся общедоступным.

**Проверка успешного доступа администратора (рисунок 8).** Роль `admin` была назначена зарегистрированной учётной записи запросом к PostgreSQL: `UPDATE users SET role = 'admin' WHERE email = 'postman-user@example.com';`. Затем в Postman отправлен запрос `POST /playlists` с JWT этой учётной записи и JSON тестового плейлиста. Сервер ответил статусом `201 Created` и вернул созданный плейлист в поле `data`. Актуальная роль пользователя загружается из базы данных при каждом защищённом запросе, поэтому после её изменения повторный вход не обязателен. Для очистки тестовых данных созданный плейлист удалён запросом `DELETE /playlists/<ID>` с Bearer-токеном администратора; сервер ответил `204 No Content`.

**Вывод.** В ходе выполнения лабораторной работы создана Sequelize-модель пользователя с уникальным email, bcrypt-хешем пароля и ролью; миграция добавляет таблицу пользователей в PostgreSQL. Реализованы регистрация `POST /auth/register` и вход `POST /auth/login`: при регистрации пароль хешируется с помощью bcrypt, а при успешном входе сервер выдаёт подписанный JWT со сроком действия один час. Middleware проверяет Bearer-токен и загружает актуальные данные пользователя из базы, а маршрут `GET /profile` возвращает профиль вошедшего пользователя без пароля и его хеша.

В качестве дополнительного механизма безопасности реализована ролевая модель RBAC. Новому пользователю назначается роль `user`; роль `admin` назначается администратором базы данных. Список плейлистов и отдельные плейлисты доступны для чтения, а создание, изменение и удаление разрешены только вошедшим пользователям с ролью `admin`. Проверка роли выполняется по базе данных при каждом защищённом запросе, поэтому изменение роли применяется сразу. В ходе работы были изучены различия аутентификации и авторизации, применение JWT и хранение паролей в виде bcrypt-хешей. Для завершения отчёта следует приложить собственные скриншоты запросов регистрации, входа, профиля, отказа `401` без токена, отказа `403` пользователю с ролью `user` и успешного запроса администратора.

## Краткая таблица проверок

| Проверка | Метод и URL | Авторизация | Ожидаемый статус |
|---|---|---|---:|
| Регистрация нового пользователя | `POST /auth/register` | Не нужна | `201` |
| Повторная регистрация того же email | `POST /auth/register` | Не нужна | `409` |
| Вход с правильным паролем | `POST /auth/login` | Не нужна | `200` |
| Просмотр своего профиля | `GET /profile` | Bearer JWT | `200` |
| Профиль без токена | `GET /profile` | Нет | `401` |
| Создание плейлиста с ролью `user` | `POST /playlists` | Bearer JWT | `403` |
| Создание плейлиста с ролью `admin` | `POST /playlists` | Bearer JWT | `201` |
| Изменение плейлиста с ролью `admin` | `PUT /playlists/:id` | Bearer JWT | `200` |
| Удаление плейлиста с ролью `admin` | `DELETE /playlists/:id` | Bearer JWT | `204` |

## Скриншоты для отчёта

Для скриншотов регистрации, входа, успешного получения профиля, ответа `401`, отказа `403` для роли `user` и успешного запроса администратора оставь видимыми метод, URL, HTTP-статус и тело ответа. Не публикуй пароль, полный JWT, `JWT_SECRET` или учётные данные PostgreSQL. В примерах отчёта используй `/playlists`, а не `/currencies`.
